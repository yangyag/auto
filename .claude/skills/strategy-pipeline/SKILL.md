# Strategy Pipeline

전략/수식/리스크 로직을 다루는 작업의 표준 작업 흐름이다. 실거래 부작용이 발생할 수 있는 영역이므로 검증 우선 원칙을 강제한다.

## 적용 판별

이 파이프라인은 다음 작업에 적용한다:
- 전략 로직 변경
- 수식 또는 계산식 추가/변경
- 예산 분배 로직 변경
- TP(Take Profit)/SL/리스크 규칙 변경
- 진입/청산 트리거 조건 변경
- 재고 비율 또는 포지션 사이징 계산 변경
- 기준값(threshold) 변경

다음 작업에는 적용하지 않는다:
- 오타, 로그 메시지, 문서 수정
- 변수명 리팩터링, 임포트 정리
- 단순 패킷 핸들러 수정 같은 비계산 영역

## 기본 흐름

```
Planner → Generator → Evaluator
```

수식, 계산, 전략 로직, 예산 분배, TP/리스크 규칙 변경이 포함되면 흐름을 다음으로 바꾼다:

```
Planner → Math Expert → Generator → Evaluator
```

비단순 작업은 가능하면 각 역할을 실제로 분리된 subagent로 나눠 수행한다. 단순 작업이라도 같은 순서의 점검 흐름은 유지한다.

## Planner

작업의 시작점. 다음을 고정한 뒤에야 다음 단계로 넘어갈 수 있다.

- 요청을 기능 단위로 쪼개고 범위와 완료 기준을 먼저 고정한다.
- 영향 파일과 선행 인터페이스를 먼저 확인한다 (Read/Grep으로 실제 파일 확인 필수, 기억으로 추정 금지).
- 실거래 부작용 없는 검증 우선 원칙을 유지한다.
- 작업에 수식/계산/전략 로직/예산 분배/TP/리스크 규칙 변경이 들어가는지 먼저 판별한다.
- 해당되면 Math Expert 단계로 넘긴다. 해당되지 않으면 바로 Generator로 넘긴다.

Planner의 출력에는 반드시 다음이 포함되어야 한다:
1. 변경 범위 (파일 단위)
2. 완료 기준 (어떤 상태가 되면 끝났다고 볼 것인가)
3. Math Expert 검토 필요 여부 (yes/no, 근거 포함)
4. 영향받는 인터페이스 목록

## Math Expert

수학적 정합성을 검증하는 단계. **이 단계는 반드시 별도 subagent로 분리한다.** 정의는 `agents/math-expert.md`를 따른다.

검증 대상:
- 수식, 계산식, 기준값
- 예산 분배 로직
- TP/SL/리스크 계산
- 트리거 조건
- 재고 비율 계산

검증 관점:
- 로직의 정합성
- 단위 일관성 (예: 수량 vs 금액, 비율 vs 절대값)
- 경계 조건 (0, 음수, 최대값, 빈 포지션)
- 계산 방향 (덧셈/뺄셈 부호, 분자/분모, 누적 vs 순간)
- 부동소수점 오차 영향

판정:
- 문제가 없으면 Generator 단계로 넘긴다.
- 수학적으로 틀리거나 불완전하면 즉시 Planner 단계로 되돌리고, 수정된 계획이 다시 Math Expert 검토를 거치게 한다.
- 절대 "대충 맞을 것 같다"로 통과시키지 않는다.

코드 스타일은 검증 대상이 아니다. 오직 로직의 수학적 정합성만 본다.

## Generator

구현 단계. **단, Math Expert 검증 대상 작업은 Math Expert 승인 전에는 절대 구현하지 않는다.**

- Planner가 고정한 범위와 완료 기준을 바꾸지 않고 구현한다.
- 즉시 다음 행동을 막는 핵심 작업은 메인 세션이 직접 처리한다. 독립적인 보조 작업만 분리한다.
- 문서나 설정 파일의 의미가 달라졌다면 관련 문서를 함께 맞춘다.
- 기존 코드 스타일을 따른다 (.NET Framework 4.8 호환, `== false` 선호, 새로 도입된 C# 기능은 코드베이스에 이미 쓰이고 있는 것만 사용).
- 최소 surgical 변경을 우선한다. 큰 리팩터링은 별도 작업으로 분리한다.

Generator는 자의적으로 범위를 확장하지 않는다. "이 김에 이것도 고치면 좋겠는데" 라는 충동은 Planner로 다시 보내는 신호다.

## Evaluator

구현 후 반드시 수행하는 별도 검토 단계. 가능하면 별도 subagent로 분리한다. 정의는 `agents/evaluator.md`를 따른다.

핵심 질문은 "돌아가는가"가 아니라 **"운영 중 깨질 지점이 남아 있는가"** 이다.

확인 항목:
- 회귀 위험 (기존 동작이 깨졌을 가능성)
- 민감정보 노출 (로그, 에러 메시지, 응답)
- 실거래 부작용 가능성 (테스트 환경에서 검증되지 않은 경로)
- Math Expert 검증 결과와 실제 구현이 일치하는가
- 경계 조건이 코드에 반영되어 있는가
- 단위가 일관되게 사용되었는가

Evaluator는 구현자와 다른 관점에서 본다. 본인이 짠 코드라도 한 번은 "처음 보는 사람" 모드로 점검한다.

## Subagent 분리 가이드

- **단순 변경** (Math Expert 불필요): 메인 세션에서 Planner → Generator → Evaluator 흐름만 머릿속으로 따라가도 된다.
- **수식/리스크 변경 (Math Expert 필요)**: Math Expert는 반드시 별도 subagent로 띄운다. Generator와 Evaluator도 가능하면 분리한다.
- **대규모 변경**: 네 단계 모두 별도 subagent로 분리한다.

## 흐름이 깨지는 신호

다음이 발생하면 흐름을 멈추고 Planner로 돌아간다:
- Generator가 Planner 범위에서 벗어난 변경을 발견했을 때
- Math Expert가 "검증 불가"를 반환했을 때 (계획에 정보가 부족하다는 뜻)
- Evaluator가 회귀 위험을 발견했을 때
- 작업 도중 새로운 수식/계산이 추가로 필요해졌을 때 (Math Expert 재검토 필요)
